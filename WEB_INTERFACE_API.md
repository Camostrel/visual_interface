# WEB_INTERFACE_API — поверхность для потребительского веб-интерфейса

> Статус: **ПРЕДЛОЖЕНИЕ / спецификация** (2026-07-07). Не реализация — карта того, куда будущая
> «потребительская» интеграция (мониторинг/управление зданием для жильцов/менеджеров) может
> обращаться, что извлекать, и где нужны НОВЫЕ эндпоинты. Уровни доступа — черновик, обсуждать
> отдельно (см. §6).

## 1. Цель и границы

**Есть сейчас:** карта `arvid-dali-panel` — это ЯДРО пусконаладки DALI (скан, адресация, привязки,
сеть шлюза, параметры). Пользователи туда НЕ допускаются.

**Хотим:** отдельный веб-интерфейс для НЕ-настройщиков:
- мониторинг активности помещений: движение, освещённость, вкл/выкл света, яркость;
- энергомониторинг;
- ошибки/здоровье устройств;
- (опц.) вкл/выкл/яркость света и создание групп света;
- ограниченное редактирование: напр. только `friendly name`, БЕЗ смены `entity_id`.

**Принцип:** потребитель работает через СТАНДАРТНЫЙ HA (сущности/сервисы/areas) + узкий набор наших
read-WS; ядро (admin-команды) ему НЕ отдаём. Комнаты = HA **areas/floors** (уже проставляются).

## 2. Что уже готово к потреблению

### 2.1 Стандартные HA-сущности (главный источник — берём нативным HA API)
Потребляются HA WebSocket (`subscribe_entities`/`get_states`), REST `/api/states`, шаблонами, любым
HA-клиентом. Управление — штатными сервисами. Комнаты — через area/floor реестры.

| Сущность | Платформа | Что даёт | Управление |
|---|---|---|---|
| Лампа | `light.*` (`DaliLight`) | вкл/выкл, яркость (1..255), CCT где есть, `available` | `light.turn_on/off/toggle` (**НЕ admin**) |
| Группа света | `light.*` (`DaliGroupLight`) | агрегат вкл/яркость по членам | `light.turn_on/off/toggle` |
| Движение | `sensor.*` (`DaliMotionSensor`) | текстовое состояние (движение/нет/свободно) | read-only |
| Освещённость | `sensor.*` (`DaliLuxSensor`, `device_class=illuminance`, lx) | люксы | read-only |
| Кнопка панели | `event.*` (`DaliPanelEvent`) | события click/hold/double/rotate/hold_end + `key_no` | read-only |
| Активация датчика | `switch.*` (`DaliSensorActiveSwitch`) | включён ли датчик в опрос | (админ-уровень по смыслу) |

> Мониторинг движения/освещённости/света/«кто где горит» строится ПОЛНОСТЬЮ на этих сущностях +
> area/floor — без наших кастомных команд. Это самый стабильный контракт (HA его не ломает).

### 2.2 Наши WS-команды БЕЗ `require_admin` (можно давать потребителю на чтение)
Транспорт — HA WebSocket, `{"type": "arvid_dali_center/…", …}`.

| Команда | Назначение | Заметка |
|---|---|---|
| `gateways` | список шлюзов (`gwSn`, имя, IP, связь) | IP — деталь инфраструктуры, можно скрывать в UI |
| `devices` `{gw_sn}` | устройства шлюза + состояние + резолв `entity_id` | база для дерева/резолва сущностей |
| `groups` `{gw_sn}` | группы + состав + `entity_id` группы | для экрана групп |
| `energy_data` `{gw_sn}` | отчёт по лампам: `power_w/energy_wh/on_time_s/real_wh` + area/floor | энергостраница |
| `energy_live` `{gw_sn}` | живой снимок мощности/энергии/алармов (RAM) | для «сейчас» |
| `get_param` `{…}` | сохранённые параметры лампы (fadeRate и т.п.) | read |
| `get_group_param` `{…}` | параметры, заданные группе | read |
| `get_sensor_param` `{…}` | параметры датчика | де-админен намеренно (v0.63) |
| `get_rotary_binding` `{…}` | привязка поворотной панели | read |
| `events` | журнал событий устройств | лента |
| `events_subscribe` | ЖИВОЙ поток событий (push в WS) | для реалтайма |
| `health_data` | здоровье/ошибки устройств (оффлайн/неизв/залипшие) | экран ошибок |

### 2.3 REST (pull, токен-авторизация HA)
- `GET /api/arvid_dali_center/energy[?format=csv]` — выгрузка энергоотчёта (JSON/CSV). Удобно для
  экспортов/отчётов потребителя без WS.

## 3. Admin-gated — потребителю НЕ отдавать (ядро)
Требуют `require_admin` (настройщик): `scan`, `set_param`, `set_param_bulk`, `forget_device`,
`set_rotary_binding`/`clear_rotary_binding`, `set_sensor_param`, `rename`, `rename_group`,
`set_address`, `restart_gateway`, `reset_addresses`, `set_gw_net`, `set_gw_name`, `identify`,
`create_group`, `set_group_members`, `del_group`, `group_reload`, `group_write`,
`panel_bindings`/`add_panel_obj`/`del_panel_obj`, `sensor_bindings`/`add_sensor_obj`/`del_sensor_obj`,
`set_lux_keep`/`read_lux_keep`/`clear_lux_keep`, `energy_set_params`, `energy_set_tariff`,
`health_clear_window`, `health_set_thresholds`.

⚠ Обрати внимание: **управление светом группой** (`group_write`) и **создание групп** (`create_group`)
сейчас под admin. Индивидуальные лампы управляются НЕ-admin сервисом `light.*`, а вот группы —
только через admin-команду. Это развилка доступа (§4, §6).

## 4. Маппинг фич веб-интерфейса → источник

| Фича потребителя | Откуда брать | Уровень |
|---|---|---|
| Движение/освещённость по комнатам | HA-сущности `sensor.*` + area/floor | read |
| Свет вкл/выкл/яркость (лампа) | `light.turn_on/off/toggle` на entity | operator (не admin) |
| Свет группой | сейчас только admin `group_write` → **нужен доступ/новый путь** | operator |
| Энергомониторинг | `energy_data`/`energy_live` + REST | read |
| Ошибки/здоровье | `health_data` | read |
| Создание/правка групп | admin `create_group`/`set_group_members` → **развилка доступа** | editor/operator |
| Только `friendly name` (без `entity_id`) | **нет подходящего эндпоинта** — `rename` меняет и entity_id и требует admin → **нужен новый** | editor |

## 5. Пробелы и предлагаемые НОВЫЕ эндпоинты

1. **`rename_friendly` (только имя, без `entity_id`).** Твой пример: пользователь даёт `friendly name`,
   но НЕ трогает `entity_id`. Текущий `rename` форсирует `entity_id` (v0.90) и под admin. Нужен лёгкий:
   меняет только `name_by_user` HA-устройства и/или `NameStore`, `entity_id` не трогает, свой гейт (не
   admin). Уникальность имён проверять как в v0.90, но без переименования сущности.
2. **Агрегат по комнате (area) одним вызовом.** `room_summary` → на каждую area: занятость (есть ли
   движение), средний/макс люкс, сколько ламп включено, суммарная мощность, число ошибок. Сейчас это
   собирается клиентом из многих источников; серверный агрегат дешевле и стабильнее (резолв area/floor
   у нас уже есть в energy/health — переиспользовать, см. долг E3).
3. **Снимок «состояние здания» (read-only).** Один эндпоинт: этажи→комнаты→(свет/движение/люкс/энергия/
   ошибки) для дашборда, чтобы не дёргать 5 команд на рендер.
4. **Управление группой без admin** (для operator): либо снять admin с `group_write` под отдельный
   гейт, либо тонкий `group_toggle`/`group_set` с проверкой прав уровня «operator».
5. **Модель прав тоньше бинарного admin** (см. §6) — ключевое, без неё «operator/editor» не выразить.

## 6. Доступ (черновик уровней — обсуждать отдельно)

HA даёт лишь **бинарный** `require_admin` (админ / не-админ) на WS-команду. Наши уровни:

| Уровень | Может | Реализация |
|---|---|---|
| **Viewer** | всё чтение (мониторинг, энергия, ошибки) | не-admin WS + HA state API |
| **Operator** | + вкл/выкл/яркость света и групп | `light.*` (есть) + группам нужен не-admin путь (§5.4) |
| **Editor** | + `friendly name`, создание/правка групп | новые/раз-админленные эндпоинты (§5.1, §5.4) |
| **Admin (настройщик)** | всё (ядро: скан/адреса/привязки/сеть) | текущие admin-команды, панель |

Варианты реализации тонких прав (выбрать позже):
- **Внешний слой:** веб-приложение поверх HA REST/WS со scoped long-lived токеном; права — на стороне
  приложения; в HA все действия идут под одним техническим НЕ-admin пользователем (но тогда любой с
  токеном = operator). Просто, но грубо.
- **Наш per-command гейт:** ввести собственную проверку роли в WS-хэндлерах (не только `require_admin`),
  роль — из настройки/стора по HA-`user_id`. Гибко, но это код в ядре.
- **HA-native:** отдельные HA-пользователи (админ/не-админ) + наш минимум не-admin команд; тоньше
  operator/editor так не выразить без п.2.

## 7. Рекомендации по архитектуре

- Потребительский интерфейс — **отдельная сущность** (своя Lovelace-карта ИЛИ внешнее веб-приложение
  на HA WS/REST), НЕ трогает `arvid-dali-panel`. Ядро остаётся у настройщиков.
- Комнаты/этажи — **HA area/floor** (единый источник; мы их уже резолвим в energy/health).
- Мониторинг строить на **стандартных сущностях** (стабильный контракт), наши WS — только для
  специфики (энергия/здоровье/журнал/группы).
- Реалтайм — `events_subscribe` + `subscribe_entities` (HA). Тяжёлые отчёты — REST (pull, токен).
- Начать с **Viewer** (только чтение, нулевой риск для ядра), затем добавлять Operator/Editor по мере
  проработки модели прав (§6) и новых эндпоинтов (§5).
