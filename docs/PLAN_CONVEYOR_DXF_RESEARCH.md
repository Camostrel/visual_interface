# Исследование конвейера планов: DXF (данные) + SVG (графика)

> **Статус: ИССЛЕДОВАНИЕ / ЧЕРНОВИК (2026-08-18). Не истина, а находки.** Подтверждается кодом.
> Разработку продолжаем в отдельной сессии. Здесь — зафиксированные результаты исследования
> пользователя + мои заметки по дизайну и открытые вопросы (помечены «⟢ заметка»).
>
> Заменяет «гадание по ближайшей подписи» из старого конвейера (см. [SVG_PLAN_SPEC §0](SVG_PLAN_SPEC.md),
> долги **A1/A2** в [DEBT.md](DEBT.md)). Ключевая идея: **не тащить CAD-смысл через SVG, а держать
> данные и графику отдельными источниками и объединять их конвертером.**

---

## 1. Что выяснили

Веб-интерфейс работает с SVG, где важны:
- `data-entity` — лампы/датчики/панели;
- `data-room-id` — помещения;
- сама SVG-геометрия — **только визуальная оболочка**.

При этом **AutoCAD остаётся основным источником структуры**, а Illustrator/Inkscape — только
способом получить удобный SVG.

## 2. Канон в AutoCAD

### Устройства — типовые блоки с атрибутами
Нотация имени: `L 5.4.27`, `MS 5.2.4`, `KP 5.3.1`. В блоке хранятся атрибуты:

```
TYPE, FLOOR, GROUP, NUMBER, NAME
```
Пример: `NAME = L 5.4.27`, `FLOOR = 5`, `GROUP = 4`, `NUMBER = 27`.

Для старого этажа сделана **разовая** автоматизация `DALI_IMPORT_LABELS` — перенесла существующие
подписи рядом с устройствами в атрибуты блоков. Сработала нормально.

### Помещения — без блоков
Канон:
```
Closed LWPOLYLINE
+ XData:
    NAME  = 501_kabinet
    FLOOR = 5
```
Дополнительно LISP рисует обычную визуальную подпись на слое `Room_number`.
Проверено на DXF — **XData действительно сохраняется**.

## 3. Что оказалось с DXF → SVG

- **Прямой импорт DXF в Inkscape неудобен:** странный масштаб, большая толщина линий, часть
  блоков теряется/разворачивается некорректно.
- **Illustrator открывает DXF гораздо лучше:** геометрия цела, подписи остаются настоящим текстом,
  слои сохранены, устройства визуально сгруппированы.
- **⚠ Ограничение (главное):** AutoCAD `ATTRIB` и `XData` **в SVG не переносятся**. Illustrator
  сохраняет графику, но не CAD-смысл.

## 4. Главный найденный подход — два источника

Не пытаться протащить CAD-атрибуты через SVG. Разделяем:

```
DXF = данные и координаты
SVG = графика
```
Конвертер получает **оба** файла и объединяет.

**Устройства:**
```
DXF block: NAME = L 5.4.27, X,Y
    ↓ единое преобразование координат (DXF → SVG)
SVG geometry  →  data-entity="light.l_5_4_27"
```

**Помещения (ещё проще):**
```
DXF LWPOLYLINE + XData (NAME=501_kabinet)
    ↓ преобразование координат
SVG room-zone  →  data-room-id="501_kabinet"
```

## 5. Точность — проверено (это не эвристика)

На текущем этаже преобразование DXF → Illustrator-SVG оказалось практически идеальным:
единое масштабирование **X ≈ 0.02216087, Y ≈ 0.02216091**, без заметного поворота и перекоса.

| Класс | Совпало |
|---|---|
| Lamp | **143/143** |
| MS | **31/31** |
| KP | **2/2** |

Ошибка порядка **~0.006–0.009 px** — фактически точное сопоставление, а не «ближайшая подпись».

## 6. Итоговая архитектура конвейера

```
AutoCAD
   ↓
canonical DXF
   ↓
Illustrator → SVG
   ↓
plan_convert
   ├─ читает блоки и XData из DXF
   ├─ вычисляет DXF → SVG transform
   ├─ сопоставляет устройства (по координате)
   ├─ переносит помещения
   ├─ добавляет data-entity / data-room-id
   ├─ проверяет ошибки
   ↓
production SVG
```

## 7. Правила, которые стоит задокументировать

**В AutoCAD:**
- 2D; `Z = 0`; единицы — **мм**;
- устройства — **только типовые блоки**;
- базовая точка блока — **по центру устройства**;
- помещения — **замкнутые LWPOLYLINE + XData**.

**В Illustrator:**
- можно масштабировать весь план **целиком**;
- **нельзя** отдельно двигать/масштабировать слои относительно друг друга;
- **нельзя** растягивать X/Y независимо;
- после импорта структура должна оставаться **геометрически целой**.

> Эти правила Illustrator — это и есть предпосылка «единого transform». Если их нарушить, единого
> преобразования не существует и сопоставление развалится (см. заметку ниже про верификацию).

## 8. ⟢ Мои заметки по дизайну и открытые вопросы (к следующей сессии)

Помечаю отдельно — это НЕ часть подтверждённого исследования, а что предстоит решить кодом.

1. **Мэппинг `NAME` → `entity_id`.** `L 5.4.27` → `light.l_5_4_27`; `MS 5.2.4` → `sensor.ms_5_2_4`
   (+ парный `il_5_2_4`, координата на `ms_`); `KP 5.3.1` → `event.kp_5_3_1`. Пробелы/точки →
   нижнее подчёркивание, латиница нижним регистром. Совпадает со схемой, что уже на объекте
   (`l_1_1_1` и т.п.). ⏳ Подтвердить префиксы/домены по `TYPE`, а не только по букве имени.
2. **Матчинг устройства = по координате, не по подписи.** Точка вставки блока (DXF) → transform →
   ищем SVG-элемент/группу в этой точке. Экспорт гарантирует ~0.006 px, значит допуск маленький, но
   нужен: при неоднозначности (два кандидата в допуске) — **падать с ошибкой, а не гадать** (страховка A1/A2).
3. **Помещения генерируем ИЗ DXF-полилинии** (вершины через transform), а не ищем в SVG. Это даёт
   **зоны по фактической геометрии стен** вместо прямоугольников → попутно закрывает остаток **Фазы 3**.
4. **Transform вычисляем из ≥2 (лучше 3) известных точек** и **верифицируем по остаткам**: если
   расхождение выше допуска — план не принимаем (Illustrator тронул объекты порознь / есть поворот/перекос).
   Отчёт по классам (143/143 и т.п.) — часть выхода конвертера.
5. **ezdxf:** подтвердить чтение и `ATTRIB` блоков, и `XData` у `LWPOLYLINE` (исследование говорит,
   что XData в DXF сохраняется — проверить на нашем ezdxf-пути).
6. **Как в SVG найти «группу устройства»?** Illustrator группирует устройства и держит слои —
   нужен надёжный признак (слой устройств / имя группы). ⏳ Открытый вопрос: договориться о слоях в SVG.
7. **`FLOOR`/`GROUP`/`NUMBER`** из атрибутов — избыточны к `NAME`, но полезны для проверки
   консистентности (`NAME` разложить и сверить с полями → ловить опечатки в чертеже).
