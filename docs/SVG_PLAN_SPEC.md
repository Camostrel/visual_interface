# SVG_PLAN_SPEC — эталон плана этажа

Как готовится план, чтобы интерфейс подхватил его без ручной расстановки.

**Входов ДВА:** `DXF` (данные и координаты) + `SVG` (графика). Объединяет их
[tools/plan_dxf.py](../tools/plan_dxf.py). Вручную в результате править нечего — включая
зоны помещений, которые теперь берутся из чертежа.

```bash
# проверить пару, ничего не записывая
python3 tools/plan_probe.py "tools/5 этаж.dxf" "tools/5 этаж.svg"

# собрать план
python3 tools/plan_dxf.py "tools/5 этаж.dxf" "tools/5 этаж.svg" \
    -o www/visual_interface/assets/floors/5_etazh.svg
```

Имя файла = **`floor_id` этажа в Home Assistant**: фронт грузит план по пути
`assets/floors/<floor_id>.svg` ([floor-page.js](../www/visual_interface/js/floor-page.js)).

---

## 1. Почему входов два

CAD знает про план всё: лампа — блок с атрибутом имени, помещение — замкнутая полилиния
с XData. Но **ни один экспорт в SVG этого не переносит**: Illustrator сохраняет графику
и теряет CAD-смысл.

Прошлый конвейер (PDF → Inkscape → `plan_convert.py`) пытался восстановить потерянное,
угадывая, «какая подпись ближе к какому значку». Это было не решаемо: подпись стоит от своей
лампы ровно настолько же, насколько лампы стоят друг от друга (замеры — [DEBT.md](DEBT.md) §A1).

Поэтому смысл и графику **не смешиваем**:

```
DXF ──→ имена, типы, координаты, помещения  ┐
                                            ├──→ plan_dxf.py ──→ эталонный план
SVG ──→ линии, значки, вся отрисовка        ┘
```

Связывает их **единое преобразование координат**: оно вычисляется по опорному классу
устройств и проверяется по остаткам. На реальном этаже остаток — **0.008 px** при размере
значка 4–27 px. Это не «сопоставление получше», это чтение готовой связи вместо её угадывания.

---

## 2. Что рисует проектировщик

### В AutoCAD (источник смысла)

- 2D, `Z = 0`, единицы — **мм**;
- устройство — **типовой блок** с атрибутами, базовая точка **в центре значка**;
- помещение — **замкнутая LWPOLYLINE** + XData приложения `VISUAL_INTERFACE_ROOM`.

Атрибуты блока:

```
TYPE, FLOOR, GROUP, NUMBER, NAME        NAME = "L 5.4.27", TYPE = "L", FLOOR = 5 …
```

XData помещения:

```
NAME  = 501_kabinet
FLOOR = 5
```

Значения `MANUFACTURER` / `MODEL` / `KEYS` конвейер не использует, но и не мешают.

### В Illustrator (источник графики)

DXF открывается Illustrator'ом (не Inkscape: тот ломает масштаб и теряет блоки), сохраняется
в SVG. Единственное требование — **не нарушить геометрическую целостность**:

- масштабировать можно **только весь план целиком**;
- **нельзя** двигать или масштабировать слои друг относительно друга;
- **нельзя** растягивать X и Y по отдельности.

Это и есть предпосылка единого преобразования. Нарушите — `plan_probe.py` увидит поворот,
перекос или разъехавшиеся масштабы и **не примет план**. Молча кривого результата не будет.

## 3. Нотация имён

| В чертеже (`NAME`) | `TYPE` | В плане (`data-entity`) |
|---|---|---|
| `L 5.4.27` | `L` | `light.l_5_4_27` |
| `MS 5.2.4` | `MS` | `sensor.ms_5_2_4` |
| `KP 5.3.1` | `KP` | `event.kp_5_3_1` |

Домен берётся **по `TYPE`**, а не по букве имени: буква — то, как устройство подписано,
`TYPE` — то, что оно есть. Незнакомый `TYPE` — ошибка, а не догадка.

> ⚠ Датчик движения и освещённости — **одно физическое устройство**, на плане одна точка `ms_`.
> Люкс-сущность `sensor.il_*` собственной точки не имеет: интерфейс находит её сам по общему
> `device_id`.

Помещение: `NAME = 501_kabinet` → `data-room-id="501_kabinet"`, и это же должно быть
**`area_id` помещения в Home Assistant**.

**Конвертер к Home Assistant не обращается.** План универсален и самодостаточен; «нет такой
сущности» или «нет такой area» — забота интерфейса, а правильность имён — зона проектировщика.

---

## 4. Что делает конвертер

1. **Читает DXF:** устройства (блоки с `NAME`) и помещения (полилинии с XData).
2. **Вычисляет преобразование** DXF → SVG по опорному классу (датчики: их немного, они
   разбросаны по плану и стоят поодиночке) и проверяет, что это **подобие** — без поворота,
   перекоса и разных масштабов по осям.
3. **Собирает значки.** Групп устройства в Illustrator-SVG нет: лампа — это `<rect>`, датчик —
   `<circle>` + `<text>`, панель — шесть элементов. Конвертер находит их **по габариту блока**:
   определение блока задаёт размер значка, вставка — масштаб, преобразование — место в SVG.
   Захватывается то, что внутри прямоугольника, а не то, что «рядом».
4. **Разрешает пересечения по составу блока.** Длинный светильник может накрыть габаритом
   текст соседнего датчика. Блок знает, из чего состоит значок, — у лампы места под текст нет,
   значит и претендовать ей не на что. Эвристики «чей ближе» в конвейере нет вовсе.
5. **Рисует зоны помещений** из полилинии DXF — по фактической геометрии стен, а не
   прямоугольником на глаз.
6. **Снимает краску чертежа**, оставляя толщины линий: цвет даёт тема интерфейса.
7. **Поджимает `viewBox`** под фактическое содержимое (Illustrator отдаёт холст с запасом).
8. **Проверяет и отчитывается.** Любая неоднозначность — отказ, а не правдоподобный результат:
   перепутанное имя лампы на плане не видно глазом, оно всплывёт через месяц не тем светом
   в не той комнате.

### Что проверяется, а что нет

Проверяется **геометрия и однозначность**: подобие преобразования, остатки, полнота захвата,
совпадение состава значка с блоком. Из данных чертежа проверяются только **дубли `NAME`** —
одинаковых устройств в проекте не бывает.

**`FLOOR` не проверяется:** линии, идущие по лестнице, законно приходят на план соседнего
этажа. Чертёж — истина, конвертер её не оспаривает.

## 5. Что на выходе

```xml
<svg viewBox="-35.83 2.45 1862.99 1075.09">
  <g id="walls">
    <line x1="230.92" y1="1032.86" x2="235.35" y2="1032.86"
          stroke-width=".26" class="plan-wall" stroke="currentColor" fill="none"/>
  </g>
  <g id="devices">
    <g id="l_5_4_27" class="device-node device-light" data-entity="light.l_5_4_27">
      <rect x="…" y="…" width="…" height="…" stroke-width=".43" .../>
    </g>
    <g id="ms_5_1_7" class="device-node device-sensor" data-entity="sensor.ms_5_1_7">
      <circle cx="238.94" cy="673.37" r="4.65" .../>
      <text transform="translate(237.38 675.21)" fill="currentColor" stroke="none">…</text>
    </g>
  </g>
  <g id="room-zones">
    <path id="501_koridor" class="room-zone" data-room-id="501_koridor" d="M … Z"/>
  </g>
</svg>
```

`data-entity` и класс висят **на группе**: датчик — это кружок и буква, панель — шесть
элементов; цвет состояния наследуется внутрь.

Подписи из чертежа (`Lamp_number`, `Sensor_number`, `Panel_number`) удаляются: имена теперь
в данных. Подписи помещений тоже — интерфейс подписывает комнату сама из HA; вернуть их можно
флагом `--keep-room-labels`.

## 6. Цвета и темы

В плане **нет собственных цветов**: везде `currentColor`, и тему задаёт интерфейс
([floor.css](../www/visual_interface/css/floor.css)).

| Элемент | Как красится |
|---|---|
| Стены `.plan-wall` | `currentColor` ← `--svg-plan-line` |
| Светильник `.device-light` | серый / оранжевый при включённом / красный при offline |
| Датчик `.device-sensor` | серый / зелёный при движении |
| Зона `.room-zone` | прозрачная / по режиму карты |

Атрибуты `stroke="currentColor"` и `fill="none"` в файле стоят намеренно, хотя CSS их
перебивает: благодаря им план читается **сам по себе** — открыл файл в браузере и видишь
чертёж, а не чёрные пятна. Для плана, который ездит по объектам отдельно от интерфейса,
это важнее экономии двух атрибутов.

**Толщины линий сохраняются** — по ним видна иерархия (несущая стена толще перегородки).

## 7. Приёмка плана

```bash
python3 tools/plan_probe.py план.dxf план.svg   # код возврата 1, если план не годен
```

План готов, если:

- [ ] пробник говорит «план принимается» (подобие, матчинг однозначен, кросс-проверка сошлась);
- [ ] число устройств по классам совпадает с проектом;
- [ ] `data-room-id` каждой зоны существует как area в Home Assistant;
- [ ] имена (`l_5_4_27`) совпадают с именами устройств в HA;
- [ ] файл назван по `floor_id` этажа, и этаж в HA существует;
- [ ] план открывается в интерфейсе и в светлой, и в тёмной теме.

**Кросс-проверка** в пробнике — главная страховка: преобразование считается по датчикам,
а проверяется на зонах помещений, которые в его вычислении не участвовали. Если оно верно
только там, где его подгоняли, это будет видно.

## 8. Старый конвейер

[tools/plan_convert.py](../tools/plan_convert.py) (PDF/Inkscape → SVG, привязка подписи
к ближайшему значку) оставлен как есть для планов старого формата. Для новых планов он
**не используется**: `assets/floors/3_etazh.svg` собран им и, вероятно, содержит перепутанные
имена — это был тестовый этаж.
