## P1 — блокирует реальный объект

### D1. Загружаем и слушаем «всё сразу»
`ArvidHaRegistry.loadAll()` тянет **все** `get_states` + 4 реестра, а подписка —
глобальный `subscribe_events(state_changed)` на весь HA. На объекте ~4400 устройств это
стоп-фактор (трафик, память, лишние события).

**Целевое** (DESIGN реш. 13): `subscribe_entities` только на сущности текущего сегмента;
их объявляет сам SVG через `data-entity`. Кешировать только статику (SVG/структуру).

**Где:** `js/ha-registry.js → loadAll()`, `js/ha-ws.js → subscribeStateChanged()`, `js/app-state.js`.
**Связано с:** D2.

### D2. `data-entity` из SVG не читается
Сейчас из плана читаются только зоны `data-room-id`. Устройства рисуются по координатам из
нашего стора. Для Сценария 1 (конвейер DWG→SVG на больших объектах) нужно читать
`data-entity="<entity_id>"` прямо из SVG и привязывать сущности из плана.

**Где:** `js/room-page.js → renderDeviceMarkers()`, `js/floor-page.js`.
**Связано с:** D1, Фаза 4 ROADMAP, требование 3.3 REQUIREMENTS.

## P2 — важно для функционала

### ~~D3. Логика режимов карты (Фаза 2)~~ — ✅ ЗАКРЫТ (v0.8.0)
Три режима работают. Освещение — оранжевый по свету; Присутствие — зелёный по `motionActive`
(свет игнорируется); Диагностика — серые линии плана, красный пульс на «не на связи», янтарный
на аномалиях. Источник диагностики — **ядро DALI** (`health_data`), своей логики offline нет.

**Где:** `js/health.js`, `js/floor-page.js → setMapMode()/applyZoneStateClasses()`, `css/floor.css`.

### ~~D4. Селект режима карты не виден на мобильном~~ — ✅ ЗАКРЫТ (v0.8.0)
Решён конструктивно, а не медиазапросом: `<select>` из `.topbar-actions` заменён
таб-переключателем `.map-mode-switch` — плавающим оверлеем над планом (как `.plan-toolbar`).
Виден одинаково на ПК и телефоне, мобильную сетку не трогает (высота плана считается от ширины
`.svg-stage`). Заодно соответствует формулировке ТЗ «переключатель-табы над картой».

### D5. Состав комнаты не пересобирается при изменении набора устройств
После v0.6.0 `render*` вызывается только при смене комнаты/этажа/режима. Если устройство
появилось, исчезло или ушло в `unavailable`, карточки не перестроятся до перехода.
Нужно: детектировать изменение состава (появление/пропажа сущности) и делать полный `render`.

**Где:** `js/room-page.js → handleStateChanged()`.

### D6. Честная обработка `unavailable` / offline в комнате (DESIGN реш. 17)
На этаже offline закрыт (v0.8.0: режим «Диагностика» + «Предупреждения», данные из `health_data`).
**В комнате — нет:** недоступное устройство выглядит как обычное. Нужно: приглушённый маркер,
статус «не на связи» в карточке, заблокированное управление.

Технически упирается в **H6**: в записях `health_data` нет `entity_id`, поэтому связать ошибку
с конкретным маркером нельзя — только с помещением. До H6 либо фолбэк на `state === 'unavailable'`
самой сущности (в комнате это допустимо: маркер = сущность), либо ждать поле от ядра.

**Где:** `js/room-page.js → renderDeviceMarkers()`, `css/room.css`.

### D7. Индикатор «ожидание» при действии (DESIGN реш. 12)
Показываем реальное состояние без оптимистики — но и без индикации, что команда ушла.
Нужен спиннер/состояние «ожидание» на контроле до прихода `state_changed`.

### D8. CCT (цветовая температура) для ламп типа 0102
В скоупе v1 (DESIGN реш. 7), не реализовано. Сейчас только вкл/выкл + яркость.

## P3 — можно жить

### D9. Мёртвый код Quick View
Отключён с v0.5.0 (решение пользователя — «закомментировать, не стирать»).
Методы `openRoomQuickView/refreshRoomQuickView/...` в `floor-page.js` и стили

### D10. `renderFloorDashboard()` всё ещё перестраивает DOM сводки
Вызывается в rAF-коалесценции (≤1 раз/кадр), так что не мигает, но по-хорошему должен
обновлять только числа, как это сделано в комнате.

**Где:** `js/floor-page.js → renderFloorSummary()`.

### D11. Расписание вне скоупа
`schedule-ui.js` + `schedule.css` + popup в `index.html` унаследованы от старого интерфейса,
работают, но в скоуп v1 не входят (DESIGN). Решить: оставить, спрятать или удалить.

### D12. «Живой» индикатор панелей (DESIGN реш. 9, 18)
Сейчас показывается только текст последнего события. Требуется мигание/подсветка при нажатии
и лента событий.

### D13. Светильники на общем плане при зуме
Опциональный пункт ТЗ: при зуме показывать светильники на плане этажа + замерить память
и быстродействие. Требует D2.

### D14. `arvid_dali_center` read-only WS — используется частично
С v0.8.0 вызываем **`health_data`** (здоровье устройств → режим «Диагностика», «Предупреждения»).
Остальное пока не трогаем: состав DALI-группы (`groups`), живой поток событий панелей
(`events_subscribe` → D12), энергия (`energy_data`/`energy_live` — вне скоупа v1).
См. [WEB_INTERFACE_API.md](WEB_INTERFACE_API.md).

### D18. Здоровье опрашивается поллингом, push-канала нет
`health_data` — снимок; подписки на изменение здоровья ядро не предоставляет. Опрашиваем раз в
300 с (30 с в «Диагностике»). Это не наш выбор, а свойство контракта: ядро всё равно не отдаст
ошибку раньше грейса `interval_min` (5 мин). Если понадобится реалтайм — просить у ядра
`health_subscribe` (аналог `events_subscribe`).

**Где:** `js/health.js → startPolling()`.

### D15. Тонкая модель прав
`layout/save` требует `require_admin`, то есть расстановку может делать только админ-токен.
Уровни Viewer/Operator/Editor из WEB_INTERFACE_API §6 не выражены.

### D16. Реальные планы объекта (Фаза 3)
`default-floor.svg` и `rooms/ofis.svg` — нарисованы нами. Нужны настоящие планы
(чистые стены, полигоны-обводки по фактической геометрии, не прямоугольники).

### D17. Фильтр по помещению в редакторе
Отложен осознанно (v0.4.0): список показывает все устройства HA + поиск. Когда area будут
заданы повсеместно, вернуть фильтр «только это помещение» как опцию.

### H6. `health_data` → добавить `area_id`, `floor_id`, `entity_id` в записи `active`
Сейчас `health/evaluator.py → _resolve()` кладёт в запись **имена**: `area = area.name`,
`floor = floor.name`. Наш интерфейс адресует зоны плана по `area_id` (`data-room-id`), а маркеры —
по `entity_id`. Поэтому:

- **area** приходится резолвить по имени через реестр HA. **Дубли имён** помещений сопоставить
  нельзя — такие записи уходят в счётчик «Без помещения» и `warn` в лог. Переименование помещения
  ломает связь до перезагрузки реестра.
- **entity_id** нет вовсе → ошибку нельзя показать на конкретном маркере устройства
  (блокирует **D6** в комнате).

`_resolve()` уже держит объекты `area`/`floor` и резолвит устройство через реестры — поля
доступны на месте, вычислять ничего не нужно.

Код фронта уже готов: `record.area_id || nameIndex.get(record.area)` — как только поле появится,
фолбэк по имени перестанет использоваться сам, правок не требуется.

**Где (ядро):** `custom_components/arvid_dali_center/health/evaluator.py → _resolve()`, `_compute()`.
**Связано с:** D6, D18.
