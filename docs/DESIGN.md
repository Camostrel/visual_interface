## ⟳ ПИВОТ (2026-07-07, после первых макетов)

Базой берём **проверенный «оконный» концепт старого `web_interface`**, а не минималистичные «обрезки».
Переупаковываем его стильно + увязываем с новым DALI-ядром + закладываем паттерн «план с устройствами».
«Declutter» относится к чистоте КОДА и паттернам, НЕ к выкидыванию фич.

**Оконный концепт (сохраняем и рестайлим):**
- 3-панельная раскладка: левая навигация (бренд, Главная/Редактор, этажи, часы/погода/тема) · центр (топбар + SVG-план этажа + зум) · правая панель общих функций (сворачиваемая).
- Правая панель: Режимы работы, Быстрые действия, **Сводка этажа**, **Расписание**, **Предупреждения**.
- **Quick-view модалка** по клику на комнату (Свет N/N кликабельно, движение) → «Открыть помещение».
  ⟳ **Итог реализации:** от Quick-view отказались (решение A). Короткий тап по зоне = toggle света
  комнаты, двойной тап = переход в комнату; полламповый тап по лампе на плане комнаты = toggle лампы.
  Код Quick View удалён в v0.10.2. Понадобится — сделаем заново на текущем функционале.
- **Вид комнаты** — со своим планом; устройства-точки живут ЗДЕСЬ (не на общем виде этажа).
- Адаптация под телефон (как в старом: аккордеоны/плавающие панели), но с лучшим мобильным вниманием.

**Что уточняем относительно строк ниже:** решения #3/#13-#16/#18 про «минимальный план-селектор и нижние панели»
ЗАМЕНЯЮТСЯ оконным концептом выше. Технические решения (стек, без backend, `data-entity` в SVG, реальное
состояние + «ожидание», честная недоступность, per-segment подписка, токенная тема, только русский,
Scenario-1 координаты) — ОСТАЮТСЯ в силе.

**Ключевое разделение (2026-07-07):** старый `web_interface` — это **референс ВЁРСТКИ** (раскладка, оконность,
панели), а **план РАБОТЫ (функции/данные) — НАШ новый** из дерева ответов. Не тащим из старого функциональность
вне скоупа. Скоуп v1 строго: **свет (управление) · движение/освещённость (мониторинг) · кнопочные/поворотные
панели (активность)**. **НЕ переносим:** климат, температуру, CO₂, влажность, шторы — их в quick-view/сводке нет.
Сводка/предупреждения/режимы/расписание — это оконные СЛОТЫ, наполняем их нашими сигналами (свет/датчики/панели),
расписание — из `binary_sensor.schedule_*` (event_schedule).

## Скоуп v1

**В скоупе:**
- Свет — мониторинг + управление (вкл/выкл, яркость, CCT где есть, группы).
- Датчики движения и освещённости — мониторинг.
- Кнопочные и поворотные панели — живой индикатор нажатий/поворотов (мониторинг активности).

## Ключевые решения

| # | Решение |
|---|---------|
| 1 | **Форма:** отдельное SPA на `/local/` (не Lovelace, не внешний хостинг). |
| 2 | **Стек:** ванильный JS + нативные Web Components, без сборщика/зависимостей. **Mobile-first — жёсткий принцип.** |
| 3 | **Навигация:** план этажа — основа; список комнат — опционально. |
| 4 | **Детализация плана:** точки-устройства; координаты берём ИЗ SVG, не из редактора. |
| 5 | **Конвейер координат v1 — Сценарий 1:** DWG → слои → SVG с уже размещёнными именованными элементами; авто-привязка по имени. Отдельной страницы редактора нет (правку координат см. решение 20). |
| 6 | **Привязка:** элемент SVG несёт `data-entity="<entity_id>"`; зоны комнат — `data-room-id="<area_id>"`. |
| 7 | **Свет:** полное управление через штатные `light.*` (не-admin): вкл/выкл + яркость (1..255) + CCT для типа 0102. «Вся комната» = отдельная DALI-группа (не изобретаем area-мастера). Группа — тоже `light.*`. |
| 8 | **Датчики:** движение/освещённость — только мониторинг. Одно устройство = две сущности (`ms_*` движение, `il_*` люкс). |
| 9 | **Панели:** `event.*`, живой индикатор нажатий/поворотов + лента событий. Активность объекта — вероятный будущий сателлит/интеграция. |
| 10 | **Доступ:** long-lived токен НЕ-admin пользователя HA в `js/config.js` (заглушка на диске, не деплоим). |
| 11 | **Backend:** своего нет. Работаем поверх стандартного HA (`subscribe_entities`, `light.*`) + существующей интеграции `arvid_dali_center` (её read-only WS). |
| 12 | **Состояние/действия:** показываем РЕАЛЬНОЕ состояние HA (без оптимистичного UI). При действии — индикатор «ожидание» на контроле до реального `state_changed`. |
| 13 | **Масштаб/скорость:** объект до ~4400 устройств, но они распределены по пространствам. На один план — десятки-сотни. **Никогда не грузим всё:** подписка `subscribe_entities` только на сущности текущего сегмента (их `data-entity` объявляет сам SVG). Кешируем ТОЛЬКО статику (SVG/структуру) для мгновенной отрисовки; показатели всегда живые. |
| 14 | **Навигация по большому плану:** сегментация ПО КОМНАТАМ (комната — атом, «край» не теряется), адаптивно к размеру/ориентации экрана; между сегментами — стрелки/селектор (как этажи). Зум/пан — запасной режим. Точную упаковку смотрим на прототипах. |
| 15 | **Взаимодействие:** точка-устройство = прямое управление; зона комнаты = подсветка по состоянию + тап открывает карточку комнаты (список устройств + мастер-контрол DALI-группы «вся комната»). |
| 16 | **Иерархия навигации:** этаж → сегмент, один объект. «Здания»/кампусы в v1 не вводим (добавим группировкой позже). |
| 17 | **Недоступность — честно:** `unavailable`/offline/зомби → приглушённая точка + статус «не на связи», управление заблокировано. Без таксономии здоровья (сателлит позже). |
| 18 | **Активность v1:** сигналы ПО ПОМЕЩЕНИЯМ — свет вкл/выкл и «датчик активен» (мигание при движении, без логирования каждого события). Механику закладываем расширяемой; детальные события/логи — отдельный разговор позже. |
| 19 | **Тема/язык:** токен-ориентированная тема (CSS-переменные, слои primitive→semantic→component) — тёмная + светлая, с заделом под КАСТОМНЫЕ палитры (будущая корпоративная оранжево-чёрно-белая — не сейчас). Язык v1 — только русский. |
| 20 | **⟳ Редактирование (правка 2026-07-07):** НЕ отдельная страница, а **режим редактирования внутри помещения** — для самостоятельной расстановки устройств. Редактор упрощён с «кучи функций» до: **список устройств помещения с фильтрами** (Все/Свет/Датчики/Панели) + перенос маркеров (drag на desktop, тап по плану на телефоне) + убрать с плана + сохранить. Настройки формы/иконки маркера удалены — **иконки в едином стиле** назначаются автоматически по типу устройства. |

## Контракт SVG (подо что готовится план из DWG)

Приложение при загрузке плана читает:
- **Устройство:** любой элемент с `data-entity="light.l_1_2_3"` (или `sensor.ms_1_2`, `sensor.il_1_2`, `event.kp_8_3_81aa`). Приложение подписывается на эту сущность, вешает состояние и (для света) управление.
- **Зона комнаты:** элемент с `data-room-id="<area_id>"` — кликабельная область, подсветка по состоянию, единица сегментации.
- **Стены/фон/подписи:** прочие элементы SVG, приложение их не трогает (стиль под тему).

Имена детерминированы (`entity_id == friendly`, префиксы `l_ / ms_ / il_ / kp_`), поэтому `data-entity` проставляется на этапе подготовки слоёв.

## Открытые вопросы / риски (на прототип)

1. **Датчик = две сущности** (`ms_`/`il_`) на одну физическую точку: одна точка тянет обе, или две точки рядом — решить визуально.
2. **Авто-сегментация по комнатам** — самый амбициозный кусок. Что если одна комната больше экрана? Как упаковывать комнаты в «страницы». Прототипировать на шаге вариаций.
3. **Группы на плане** — группа не физическая точка. Где её контрол: в карточке комнаты / отдельный чип на зоне. Деталь UX.
4. **Живые события панелей** — `event.*` через `subscribe_entities` (обычно достаточно) vs `events_subscribe` существующей интеграции. Уточнить при реализации.
5. **Визуализация состояния на плане** (свет вкл/яркость/движение/люкс) — цвет/свечение точки, тон зоны. Смотрим на вариациях (шаг 5).
