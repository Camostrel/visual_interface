# Changelog — ARVID Visual Interface

## v0.8.2 — 2026-07-10 — живая подписка на здоровье, зелёный пульс присутствия, синий выбор

Ядро выпустило **v1.1.1** в ответ на наш запрос H6 — и дало больше, чем просили.

### Изменено — здоровье: поллинг → push-подписка

- **`health_subscribe`** (не-admin, ядро ≥ v1.1.1) вместо опроса `health_data`.
  Снимок приходит сразу, дальше ядро само шлёт его на каждый пересчёт. Таймеров нет.
- **Почему это важно, а не косметика:** `health_data` **форсирует полный пересчёт здоровья на
  каждый запрос** — обход всех устройств всех шлюзов + резолв трёх реестров на каждое, синхронно
  в петле HA. Две открытые вкладки = два прохода по ~4400 устройствам. Подписка пересчёт не
  вызывает: она получает результат чужого. (Неэффективность самой `health_data` — долг ядра HD1.)
- **Фолбэк сохранён:** `unknown_command` → старое ядро → прежний поллинг `health_data`
  (300 с, 30 с в «Диагностике»). Временная ошибка (`not_found`, обрыв) → повтор подписки через 60 с.
- Новый `ArvidHaWebSocket.subscribeCommand()` — подписка на произвольную WS-команду с push-событиями.

### Исправлено — фактическая ошибка в наших доках (D18)

Мы писали: «ядро не отдаст ошибку раньше грейса `interval_min` (5 мин), поэтому опрашивать чаще
бессмысленно». **Это верно только для устройств.** Для `gw_offline` грейса нет вовсе — оценщик
ставит его через ~1.5 с после сигнала связи (`_EVAL_DEBOUNCE`). То есть самое срочное событие
мониторинга здания, «шлюз упал», поллинг задерживал на срок до 300 с. Подписка это снимает.
**D18 закрыт.**

### Добавлено — адресация записей (H6 закрыт ядром)

Записи `active` теперь несут `area_id`, `floor_id`, `entity_id` и — сверх запроса — `device_id`.
Индексы `byAreaId` / `byDeviceId` / `byEntityId`, методы `statsForDevice()` / `statsForEntity()`.

> ⚠ **Пара движение+люкс — одно устройство HA, но ДВЕ записи здоровья** (`…:0201` и `…:0202`) с
> разными `entity_id` (`sensor.ms_*` / `sensor.il_*`) и **общим `device_id`**. На плане это один
> маркер, и координата хранится под `ms_`. Значит ошибка `lux_stale` с `entity_id = sensor.il_*`
> до маркера по entity_id **не доедет** — сопоставлять надо по `device_id`. Он же не меняется при
> переименовании, в отличие от `entity_id` (ядро форсирует его с v0.90).

Резолв `area_id` идёт по первой ветке (`record.area_id`), фолбэк по имени **оставлен**: до первой
оценки после рестарта HA (≤15 с) `active` отдаётся из персиста в старой форме, без новых полей.

Это разблокировало **D6** (offline на маркере в комнате) и сняло одну из двух блокировок Фазы 3.5.

### Изменено — цвета карты

- **«Присутствие»: зона теперь пульсирует зелёным**, как проблема в «Диагностике», но **медленнее**
  (2.6 с против 1.7 с). Движение — норма, а не авария; мигать оно должно спокойнее.
- **Выбор зоны (hover/`is-active`) стал синим.** Раньше это был `--accent`, а он зелёный (#27d09a) —
  и наведение путалось с индикацией движения. Новые токены темы `--zone-select` /
  `--zone-select-line`; глобальный `--accent` не тронут.
- На пульсирующих зонах заливку задаёт анимация (она сильнее обычных правил), поэтому выбор там
  показывается **синим контуром**, а не заливкой.
- `prefers-reduced-motion` — оба пульса заменяются статичной заливкой того же смысла.

## v0.8.1 — 2026-07-10 — реалтайм починен, движение читается верно, карта только смотрит

Разбор после первой проверки v0.8.0 на объекте. Два бага **существовали до Фазы 2** и просто
стали заметны, когда появился режим «Присутствие».

### Исправлено

- **Fix B — движение НИКОГДА не считалось активным.** `ArvidDeviceUi.isMotionActive()` сверял
  состояние с `motion` / `occupancy` / `no_motion` / `vacant` — «по договорённости ядра». Такой
  договорённости в коде ядра нет: `transport/decode.py` отдаёт **русский текст**
  `{1:"нет движения", 2:"ДВИЖЕНИЕ", 3:"свободно", 4:"занято", 5:"пост.занято"}`.
  Ни одно значение не совпадало → функция всегда возвращала `false`.
  Следствия: режим «Присутствие» не красил зоны (не мог в принципе), сводка этажа «Движение»
  всегда показывала 0, в комнате «Движение: нет», маркер датчика никогда не подсвечивался.
  Активными считаем `ДВИЖЕНИЕ` / `занято` / `пост.занято`.
  > ⚠ Сравнивать только **полным** значением: «нет движения» содержит подстроку «движение»,
  > поэтому любой `includes("движ")` даст ложное срабатывание.

- **Fix C — комната не обновлялась по `state_changed` вообще.** В `room-page.js` подписка была
  `addStateHandler(() => this.handleStateChanged())` — стрелка **без аргумента**, поэтому
  `handleStateChanged(event)` получал `undefined`, читал `event?.data?.entity_id` и выходил на
  первой же проверке. Люксы, движение и счётчик «N/N включено» обновлялись только при перезаходе
  в комнату. Теперь событие пробрасывается: `addStateHandler((event) => this.handleStateChanged(event))`.

- **Fix D — кеш состава комнаты.** Подписка на `state_changed` глобальная, поэтому
  `isRoomEntityId()` зовётся на **каждое** событие HA, а он пересобирал состав комнаты
  (полный резолв area по всем сущностям). Из-за Fix C этот путь никогда не исполнялся — после
  починки стал бы горячим. Состав кешируется в `Set`, сбрасывается при смене комнаты и после
  сохранения разметки.

### Изменено

- **Карта вне «Освещения» — только смотрит.** Одиночный тап по зоне переключал свет в любом
  режиме; в «Присутствии»/«Диагностике» случайный тап гасил свет в помещении, за которым
  наблюдают. Теперь одиночный тап работает только в «Освещении» (`canToggleLightsFromMap()`),
  двойной тап (переход в комнату) — во всех режимах.
- `Enter`/`Пробел` на зоне: в «Освещении» — свет, в остальных режимах — переход в комнату.
  Подпись `aria-label` зоны следует режиму (`updateZoneAriaLabels()`, обновляется и по смене режима).

### Документация

- REQUIREMENTS §4.1 — полная таблица «вид ошибки ядра → метка → поведение на карте».
- ROADMAP — Фаза 3.5: проблемные лампы на плане этажа при зуме (просьба заказчика).

## v0.8.0 — 2026-07-10 — режимы карты (Фаза 2), здоровье от ядра DALI

Закрывает долги **D3** (логика режимов) и **D4** (селектор не виден на мобильном),
частично **D14** (read-only WS ядра) и **D6** (обработка offline на уровне этажа).

### Добавлено

- **Три режима карты** (селектор был с v0.6.1, логики не было):
  - **Освещение** — как раньше: оранжевый по включённому свету.
  - **Присутствие** — свет игнорируется, зелёным горят зоны с движением.
  - **Диагностика** — линии плана гаснут до серого, **красным пульсируют** зоны с устройствами
    не на связи, **янтарным** — зоны с аномалиями (залипшее движение, «мёртвый» люкс).
- **`js/health.js` (`ArvidHealth`)** — клиент здоровья устройств. Данные берём у ядра DALI
  (`arvid_dali_center/health_data`, read-only, без `require_admin`), **своей логики offline не ведём**.
- **Слот «Предупреждения»** наполнен: упавшие шлюзы, помещения с offline/аномалиями,
  счётчик записей без помещения. Раньше там была заглушка «Предупреждений нет».
- `ArvidDeviceUi.isScoped()` — общий фильтр скоупа (был приватным дублем в `room-page.js`).

### Изменено

- **Переключатель режимов** из `<select>` в топбаре стал **таб-переключателем над картой**
  (`.map-mode-switch`, оверлей как `.plan-toolbar`). На телефоне `.topbar-actions` скрыт —
  раньше режим там был недоступен; теперь контрол одинаков на ПК и телефоне (**D4**).
- `applyRoomLightHighlight()` → **`applyZoneStateClasses()`**: вешает на зону сразу все классы
  состояния (`has-light-on` / `has-motion` / `has-offline` / `has-anomaly`), а видимый слой
  выбирает CSS по `data-map-mode` на `.svg-stage`. Смена режима = один атрибут, без пересчёта;
  инвариант «DOM не перестраивается по `state_changed`» сохранён. Заодно `getRoomStats()`
  вызывается один раз на зону вместо одного на каждое состояние.
- `getRoomStats()` отдаёт `offlineCount` и `anomalyCount` (из снимка health).

### Исправлено

- **Fix A — движение по всем датчикам помещения.** `motionActive` считался по **первому**
  найденному датчику (`entities.find`), поэтому в комнате с несколькими датчиками сработка
  на втором и далее игнорировалась — и в подсветке зон, и в сводке «Движение».
  Теперь `some()` по всем датчикам движения помещения.

### Решения (важно для понимания)

- **Диагностику не считаем сами.** Ядро уже ведёт таксономию ошибок (`HEALTH.md`): `lamp_offline`,
  `lamp_unknown`, `sensor_unknown`, `panel_unknown` → «не на связи» (красный пульс);
  `motion_stuck`, `motion_idle`, `lux_stale` → «аномалия» (янтарный); `gw_offline` → строка в
  «Предупреждениях» (шлюз к помещению не привязан).
- **Частота опроса.** У health нет push-канала, только снимок. Ядро не считает устройство
  сломанным первые `grace = interval_min` (**5 минут**) — защита от транзиентов при рестарте.
  Значит опрашивать чаще бессмысленно: в фоне **300 с**, в режиме «Диагностика» **30 с**
  (чтобы починенная зона гасла быстро), при скрытой вкладке — пауза, при возврате — свежий снимок.
- **Серость карты** сделана цветом линий плана (`--muted`), а **не** `filter: grayscale()`:
  фильтр обесцветил бы и сам красный пульс.
- **Деградация без ядра.** `unknown_command` → модуль выключается, поллинг останавливается,
  «Предупреждения» показывают «Данные о здоровье недоступны», режимы Освещение/Присутствие
  работают как обычно. Обрыв WS — временная ошибка, снимок сохраняется, поллинг живёт.

### Известное ограничение

`health_data` отдаёт **имя** помещения (`area.name`), а не `area_id`. Зоны плана живут по
`area_id`, поэтому имя резолвится через реестр HA; **дубли имён** сопоставить нельзя (уходят в
счётчик «Без помещения» + `warn` в лог). Запрос к ядру — добавить `area_id`/`floor_id`/`entity_id`
в записи (**H6** в [DEBT.md](DEBT.md)); код подхватит поле без правок.

## v0.7.0 — 2026-07-08 — состав комнаты = HA-area (истина), непривязанные помечены

### Изменено (важно)

- **Состав комнаты теперь определяется только Home Assistant** (`entity/device.area_id`),
  а не объединением «HA-area ∪ размещённые на плане» (как было с v0.4.0).
  Причина: объединение делало состав непрозрачным — в «Офисе» показывалось 9 ламп,
  хотя в HA к нему привязана только часть, остальные попали туда через расстановку на плане.
  По составу считаются карточки, счётчики «N/N включено» и статистика комнаты.
- **Маркеры на плане** рисуются по нашему layout (у кого есть координаты) — как и раньше.
- **Непривязанные помечаются:** устройство стоит на плане комнаты, но в HA к ней не привязано →
  маркер приглушён и обесцвечен (`.device-marker.is-unassigned`), а в комнате появляется плашка
  «N устр. на плане не привязано к помещению в HA».

Новое в API: `ARVID_APP.entitiesForArea()` (состав), `placedEntitiesForRoom()` (маркеры),
`isUnassignedInRoom()`. `entitiesForRoom()` (объединение) остался только как фильтр
«свои события» для подписки.

## v0.6.0 — 2026-07-08 — HA-группы света, конец перерисовки UI, docs/

### Исправлено

- **Fix A — мигание кнопок и слайдера при потоке показаний.** `handleStateChanged` вызывал
  полную перестройку DOM (`renderControls` делал `innerHTML=""`), а на этаже ещё и
  `bindRoomZones()` перевешивал все обработчики зон — на **каждое** `state_changed`.
  При включении света поток от люкс-датчика давал десятки перестроек в секунду.
  Разделены **render** (построение) и **update** (только значения):
  - фильтр чужих сущностей + коалесценция событий в один кадр (`requestAnimationFrame`);
  - точечное обновление по якорям `data-entity`, `data-light-count`, `data-sensor-anchor`,
    `data-panel-entity`, `data-mode-entity`;
  - слайдер яркости не трогается, пока пользователь его держит или он в фокусе;
  - `bindRoomZones()` больше не вызывается по `state_changed`.

### Изменено

- **Управление светом — через HA-группы, а не поиск ламп** (детерминированно):
  комната → `light.<area_id>` (например `light.ofis`), этаж → `light.<floor_id>`
  (например `light.3_etazh`). Хелпер `ARVID_APP.lightGroupState()`. Если группы нет —
  фолбэк на сборку ламп + предупреждение в лог. Групповая сущность исключена из счётчиков
  «N/N включено» и из списка ламп-членов. Затронуты: тап по зоне, «Вся комната» в карточке
  освещения, «Выключить свет этажа».
- **Документация переехала в `docs/`** (ARCHITECTURE, DESIGN, DEPLOY, ROADMAP,
  WEB_INTERFACE_API, CHANGELOG). `CLAUDE.md` остался в корне.

### Добавлено

- **docs/REQUIREMENTS.md** — живой чек-лист «требование → как реализовано у нас» с указанием
  файлов и методов (в т.ч. подробно: зум/пан, полигоны помещений, подсветка).

### Удалено

## v0.4.1 — 2026-07-08 — иконки в редакторе, единый датчик, клик-размещение

### Исправлено

- **Fix A — пустые чёрные иконки в редакторе.** Рамка выделения (`rect.device-marker-selection`)
  добавлялась поверх иконки, а CSS-селектор `.device-marker rect:not(.device-marker-hit)`
  заливал её тёмным (специфичность выше `.device-marker-selection`). Исключил selection
  из заливки — иконки в редакторе теперь как на обычной странице.
- **Fix B — датчики движения (`ms_`) не появлялись в списке.** У DALI-датчиков движения
  `device_class` пустой, а `isMotion` ждал его. Добавил распознавание по префиксу `ms_`
  (и `il_` для освещённости). Причина «доступны только il_» устранена.

### Изменено

- **Единый датчик движения+освещённости.** Пара `sensor.ms_*` + `sensor.il_*` — одно
  физическое устройство (общий `device_id`), теперь это **одна точка** на плане и одна
  строка в списках (kind `sensor`, иконка-радар). Показания — оба сразу: движение · lx
  (в карточке комнаты и в попапе маркера). Схлопывание — `collapseToUnits` по `device_id`,
  якорь пары — сущность движения.
- **Fix C — размещение щелчком/тапом.** Раньше клик по плану ставил устройство только на
  телефоне (на ПК — лишь «В центр плана»). Теперь: выбрал устройство → щёлкнул/тапнул по
  месту → появилось (и на ПК, и на телефоне). Клик отличается от панорамирования по сдвигу.

### Новое в API модулей

- `ha-registry`: `getDeviceId(entityId)`, `getEntitiesForDevice(deviceId)` — для связи пары ms_/il_.
- `device-ui`: `isSensor`, единый `markerKind === "sensor"`; `room-page`: `collapseToUnits`,
  `getSensorReadings`, `formatSensorReadings`.

  и «убрать с плана». Фикс: единый фильтр скоупа `getScopedEntities()` и для плана, и для
